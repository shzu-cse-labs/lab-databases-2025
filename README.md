# lab-databases-2025
Practical exercises in SQL, schema design, normalization, indexing, and transaction management using a relational DBMS.

## 📝 قوانین تحویل گزارش

1. هر دانشجو باید برای هر آزمایش یک فایل `report.md` در پوشه همان آزمایش ایجاد کند.
2. اسکریپت‌های SQL باید در پوشه `sql/` با نام‌گذاری مشخص (مثلاً `lab01.sql`) ذخیره شوند.
3. گزارش باید شامل بخش‌های زیر باشد:
   - هدف آزمایش
   - Schema و نمودار ER
   - کوئری‌های SQL
   - نتایج خروجی
   - تحلیل نتایج (شامل `EXPLAIN ANALYZE`)
   - نتیجه‌گیری
4. مهلت تحویل هر آزمایش: یک هفته پس از انجام آزمایش.

## 🔬 آزمایش ۱: نصب PostgreSQL و طراحی Schema

### 🎯 هدف
نصب PostgreSQL 18، آشنایی با `psql` و `pgAdmin`، و طراحی یک Schema ساده برای یک فروشگاه آنلاین.

### 📚 تئوری
- PostgreSQL یک سیستم مدیریت پایگاه داده شیء-رابطه‌ای (ORDBMS) متن‌باز است که از استاندارد SQL پشتیبانی می‌کند.
- PostgreSQL 18 قابلیت‌های جدیدی مانند I/O ناهمزمان (AIO) با عملکرد تا ۳ برابر بهتر در خواندن از حافظه، و تابع `uuidv7()` برای تولید شناسه‌های مرتب‌شده با زمان ارائه می‌دهد.
- Schema طراحی شده باید حداقل در سطح **3NF** نرمال‌سازی شود.

### 🧰 وسایل مورد نیاز
- PostgreSQL 18 (نصب روی لینوکس/مک/ویندوز یا Docker)
- pgAdmin 4 یا `psql`
- کامپیوتر

📚 تئوری
ایندکس ساختاری است که جستجو را سریع‌تر می‌کند (مانند فهرست کتاب).

PostgreSQL 18 قابلیت Skip Scan روی ایندکس‌های B-tree چندستونه را معرفی کرده که کوئری‌هایی که شرط = روی ستون‌های پیشوندی ندارند را سریع‌تر می‌کند.

🔬 آزمایش ۵: توابع پنجره‌ای (Window Functions)
🎯 هدف

📚 تئوری

ROW_NUMBER() شماره ردیف متوالی می‌دهد.

RANK() با پرش در رتبه‌های مساوی کار می‌کند، DENSE_RANK() بدون پرش.

LAG() و LEAD() به ردیف قبلی و بعدی دسترسی می‌دهند.

کوئری بنویسید که رتبه هر محصول را بر اساس مجموع فروش مشخص کند (RANK).

کوئری بنویسید که تفاوت مبلغ هر سفارش با سفارش قبلی همان مشتری را نشان دهد (LAG).

کوئری بنویسید که برای هر ماه، مجموع فروش و مجموع فروش ماه قبل را نمایش دهد.

🔬 آزمایش ۶: Viewها و CTEها (Common Table Expressions)
🎯 هدف
ایجاد View برای ساده‌سازی کوئری‌های پیچیده و استفاده از CTE برای خوانایی بهتر.

📚 تئوری
View یک جدول مجازی است که از یک کوئری ساخته می‌شود و داده ذخیره نمی‌کند.

CTE با WITH تعریف می‌شود و یک نتیجه موقت برای کوئری اصلی فراهم می‌کند.

CTE بازگشتی (WITH RECURSIVE) برای پیمایش سلسله‌مراتبی استفاده می‌شود.

🧰 وسایل مورد نیاز
دیتابیس shopdb

📝 مراحل انجام کار
یک View ایجاد کنید که خلاصه سفارش‌ها (id سفارش، نام مشتری، تعداد اقلام، مبلغ کل) را نمایش دهد.

از View در یک کوئری SELECT استفاده کنید.

یک CTE بنویسید که مجموع فروش هر مشتری را محاسبه کند و سپس مشتریان برتر را فیلتر کند.

یک CTE بازگشتی بنویسید که ساختار سلسله‌مراتبی دسته‌بندی محصولات را پیمایش کند (اگر جدول categories با parent_id دارید).

View را با CREATE OR REPLACE VIEW به‌روزرسانی کنید.

EXPLAIN یک کوئری که از View استفاده می‌کند را بررسی کنید (View به کوئری اصلی بازنویسی می‌شود).

💡 مثال کاربردی
Viewها برای کنترل دسترسی (کاربر فقط به View دسترسی دارد، نه جدول اصلی) و ساده‌سازی گزارش‌ها استفاده می‌شوند. CTEها کوئری‌های پیچیده را به بخش‌های قابل فهم تقسیم می‌کنند. CTE بازگشتی برای ساختارهای درختی (مثل دسته‌بندی محصولات، ساختار سازمانی) ضروری است.

🧪 تمرین افزوده
یک View ایجاد کنید که فقط محصولات فعال (با موجودی بیشتر از صفر) را نمایش دهد. سپس یک کوئری بنویسید که از این View برای محاسبه ارزش کل موجودی استفاده کند.

🔬 آزمایش ۷: تراکنش‌ها و کنترل همزمانی
🎯 هدف
آشنایی با BEGIN، COMMIT، ROLLBACK و سطوح Isolation در PostgreSQL.

📚 تئوری
تراکنش مجموعه‌ای از عملیات است که یا همه با موفقیت انجام می‌شوند یا هیچ‌کدام (ACID).

PostgreSQL از MVCC (Multi-Version Concurrency Control) استفاده می‌کند.

سطوح Isolation: READ COMMITTED (پیش‌فرض)، REPEATABLE READ، SERIALIZABLE.

SAVEPOINT امکان بازگشت به یک نقطه میانی را فراهم می‌کند.

🧰 وسایل مورد نیاز
دیتابیس shopdb

دو ترمینال psql (برای شبیه‌سازی همزمانی)

📝 مراحل انجام کار
یک تراکنش با BEGIN شروع کنید، یک سفارش جدید درج کنید و ROLLBACK بزنید. بررسی کنید که سفارش ثبت نشده است.

همان تراکنش را با COMMIT انجام دهید و ثبت شدن را تأیید کنید.

در ترمینال اول، یک تراکنش با BEGIN شروع کنید و موجودی یک محصول را کم کنید (بدون COMMIT).

در ترمینال دوم، سعی کنید همان محصول را بخوانید. چه اتفاقی می‌افتد؟

سطح Isolation را به SERIALIZABLE تغییر دهید و رفتار را مقایسه کنید.

یک تراکنش با SAVEPOINT تعریف کنید، یک عملیات انجام دهید، به SAVEPOINT برگردید و عملیات دیگر انجام دهید.

سناریوی "انتقال پول بین دو حساب" را با تراکنش پیاده‌سازی کنید و اطمینان حاصل کنید که در صورت خطا، هیچ تغییری اعمال نمی‌شود.

💡 مثال کاربردی
تراکنش‌ها در سیستم‌های بانکی (انتقال وجه)، فروشگاهی (کاهش موجودی و ثبت سفارش) و هر جایی که چند عملیات باید به صورت اتمیک انجام شوند، حیاتی هستند. MVCC در PostgreSQL اجازه می‌دهد خواندن‌ها بدون قفل کردن نوشتن‌ها انجام شوند و عملکرد همزمانی را بهبود می‌دهد.

🧪 تمرین افزوده
سناریوی "دو کاربر همزمان یک محصول را خریداری می‌کنند" را شبیه‌سازی کنید. با SELECT ... FOR UPDATE از فروش بیش از موجودی جلوگیری کنید.

🔬 آزمایش ۸: توابع و رویه‌های ذخیره‌شده (PL/pgSQL)
🎯 هدف
نوشتن توابع و رویه‌های ذخیره‌شده با PL/pgSQL و مدیریت خطا.

📚 تئوری
PL/pgSQL زبان رویه‌ای PostgreSQL است که به SQL اجازه می‌دهد منطق شرطی، حلقه و مدیریت خطا داشته باشد.

CREATE FUNCTION یک تابع برمی‌گرداند (می‌تواند در SELECT استفاده شود).

CREATE PROCEDURE یک رویه است که با CALL اجرا می‌شود و می‌تواند COMMIT/ROLLBACK داشته باشد.

بلوک BEGIN ... EXCEPTION ... END برای مدیریت خطا استفاده می‌شود.

EXPLAIN ANALYZE یک کوئری که تابع را صدا می‌زند بررسی کنید.

💡 مثال کاربردی
توابع و رویه‌های ذخیره‌شده منطق تجاری را در دیتابیس متمرکز می‌کنند و از تکرار کد در اپلیکیشن جلوگیری می‌کنند. Triggerها برای حفظ یکپارچگی داده (مثل به‌روزرسانی خودکار موجودی یا ثبت لاگ تغییرات) استفاده می‌شوند. در سیستم‌های بانکی، رویه‌های ذخیره‌شده انتقال وجه را به صورت اتمیک انجام می‌دهند.

🧪 تمرین افزوده
یک Trigger بنویسید که هر بار قیمت یک محصول تغییر می‌کند، قیمت قدیم و جدید را در جدول price_history ثبت کند.

🔬 آزمایش ۹: نقش‌ها، مجوزها و امنیت
🎯 هدف
ایجاد نقش‌ها (Roles)، اعطای مجوزهای دقیق و پیاده‌سازی امنیت در سطح ردیف (RLS).

📚 تئوری
PostgreSQL از نقش‌ها برای مدیریت دسترسی استفاده می‌کند (CREATE ROLE).

GRANT و REVOKE مجوزهای SELECT، INSERT، UPDATE، DELETE را کنترل می‌کنند.

Row-Level Security (RLS) به شما اجازه می‌دهد دسترسی به ردیف‌های خاص را بر اساس کاربر محدود کنید.

🧰 وسایل مورد نیاز
دیتابیس shopdb

📝 مراحل انجام کار
یک نقش app_readonly ایجاد کنید و فقط مجوز SELECT روی جداول products و orders بدهید.

یک نقش app_writer ایجاد کنید که مجوز INSERT/UPDATE روی orders و order_items داشته باشد.

با SET ROLE نقش‌ها را تست کنید و مطمئن شوید که دسترسی‌های غیرمجاز رد می‌شوند.

RLS را روی جدول orders فعال کنید:

sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY user_orders ON orders
    FOR SELECT USING (customer_id = current_user_id());
یک تابع current_user_id() بسازید که شناسه مشتری را از current_setting برگرداند.

تست کنید که هر مشتری فقط سفارش‌های خودش را می‌بیند.

یک Backup با pg_dump بگیرید و روی یک دیتابیس تست بازیابی کنید.

💡 مثال کاربردی
در یک اپلیکیشن چندکاربره، نقش‌ها از دسترسی غیرمجاز جلوگیری می‌کنند. RLS در سیستم‌های SaaS (که هر مشتری فقط داده‌های خودش را می‌بیند) و در سیستم‌های بهداشتی (که هر پزشک فقط پرونده بیماران خودش را می‌بیند) حیاتی است. pg_dump برای پشتیبان‌گیری دوره‌ای و pg_restore برای بازیابی استفاده می‌شود.

🧪 تمرین افزوده
یک نقش auditor ایجاد کنید که فقط به جدول price_history (از تمرین آزمایش ۸) دسترسی SELECT داشته باشد و نتواند جداول دیگر را ببیند.

🔬 آزمایش ۱۰: پروژه پایانی – طراحی و پیاده‌سازی یک سیستم پایگاه داده کامل
🎯 هدف
طراحی، پیاده‌سازی و مستندسازی یک سیستم پایگاه داده کاربردی با PostgreSQL.

📚 موضوعات پیشنهادی (یکی را انتخاب کنید)
سیستم رزرو هتل: مدیریت اتاق‌ها، مشتریان، رزروها و پرداخت‌ها.

سیستم کتابخانه: مدیریت کتاب‌ها، اعضا، امانت‌ها و جریمه‌ها.

سیستم مدیریت پروژه: مدیریت پروژه‌ها، وظایف، اعضا و زمان‌بندی.

سیستم فروشگاه آنلاین: گسترش shopdb با دسته‌بندی، نظرات و تخفیف‌ها.

سیستم ثبت‌نام دانشگاه: مدیریت دانشجویان، دروس، اساتید و نمرات.

📝 مراحل انجام کار
موضوع پروژه را انتخاب کنید و نمودار ER کامل را طراحی کنید.

Schema را در PostgreSQL پیاده‌سازی کنید (با رعایت 3NF و کلیدهای خارجی).

داده‌های نمونه (حداقل ۵۰ ردیف در جداول اصلی) وارد کنید.

کوئری‌های تحلیلی (حداقل ۵ کوئری شامل JOIN، GROUP BY، Window Function) بنویسید.

ایندکس‌های مناسب را ایجاد کنید و با EXPLAIN ANALYZE بهبود عملکرد را نشان دهید.

یک View برای گزارش‌های پرکاربرد ایجاد کنید.

یک رویه ذخیره‌شده برای منطق تجاری اصلی (مثلاً ثبت رزرو) بنویسید.

نقش‌ها و مجوزهای مناسب را تعریف کنید.

Backup بگیرید و بازیابی را تست کنید.

گزارش کامل شامل نمودار ER، Schema، کوئری‌ها، تحلیل عملکرد و مستندات تهیه کنید.

در جلسه پایانی، پروژه را به صورت عملی демонстрация کنید.

📌 نکات ایمنی
در کار با PostgreSQL، از دستورات DROP با احتیاط استفاده کنید (مخصوصاً DROP DATABASE).

قبل از اجرای هر آزمایش، از دیتابیس Backup بگیرید (pg_dump).

در سناریوهای همزمانی، از دو ترمینال جداگانه استفاده کنید تا رفتار Isolation را به‌درستی مشاهده کنید.

در صورت استفاده از Docker، مطمئن شوید که داده‌ها روی Volume ذخیره می‌شوند تا با حذف کانتینر از بین نروند.
