# lab-databases-2025
Practical exercises in SQL, schema design, normalization, indexing, query optimization, transactions, stored logic and security using a relational DBMS (PostgreSQL 18).

---

## 🎓 نتایج یادگیری (CLO)

پس از گذراندن این آزمایشگاه، دانشجو قادر است:

1. از مشخصات یک مسئله، نمودار ER و Schema رابطه‌ای نرمال‌شده (تا 3NF/BCNF) با قیدهای یکپارچگی مناسب طراحی کند.
2. کوئری‌های تحلیلی پیچیده (JOIN، زیرکوئری، توابع پنجره‌ای، CTE) بنویسد و درستی آن‌ها را راستی‌آزمایی کند.
3. طرح اجرای کوئری (`EXPLAIN (ANALYZE, BUFFERS)`) را بخواند و با ایندکس‌گذاری مناسب عملکرد را **با اندازه‌گیری** بهبود دهد.
4. رفتار تراکنش‌ها، MVCC و سطوح Isolation را در عمل نشان دهد و با ناهنجاری‌های همزمانی (lost update، write skew، deadlock) برخورد کند.
5. منطق تجاری را با توابع، رویه‌ها و تریگرها پیاده‌سازی و تست کند.
6. دسترسی (نقش‌ها، RLS) و پشتیبان‌گیری/بازیابی را طراحی و **تأیید** کند.

## 🔬 آزمایش ۱: نصب PostgreSQL و طراحی Schema

### 🎯 هدف
نصب PostgreSQL، آشنایی با `psql`، و طراحی Schema یک فروشگاه آنلاین با انتخاب درست نوع داده و قیدها.

### 📋 پیش‌گزارش
1. نمودار ER فروشگاه را (مشتری، دسته‌بندی، محصول، سفارش، اقلام سفارش) با کاردینالیتی روابط رسم کنید.
2. برای هر ستون نوع داده مناسب انتخاب و دلیل بنویسید (چرا `numeric` برای پول و نه `float`؟ چرا `timestamptz`؟).
3. توضیح دهید چرا ستون «مبلغ کل سفارش» در جدول `orders` **نباید** ذخیره شود (داده مشتق‌شده و خطر ناسازگاری) و چگونه محاسبه می‌شود.

### 📚 تئوری
- PostgreSQL یک سیستم مدیریت پایگاه داده شیء-رابطه‌ای متن‌باز و سازگار با بخش بزرگی از استاندارد SQL است.
- کلید اصلی: ترجیحاً `GENERATED ALWAYS AS IDENTITY` (جایگزین استاندارد `serial`) یا `uuid` (در ۱۸ با `uuidv7()` مرتب‌شده با زمان).
- قیدها (`NOT NULL`، `UNIQUE`، `CHECK`، `FOREIGN KEY`) یکپارچگی را در سطح دیتابیس تضمین می‌کنند، نه فقط در برنامه.
- ستون `unit_price` در `order_items` **عمداً** قیمت لحظه فروش را نگه می‌دارد (تغییر قیمت محصول نباید سفارش‌های قدیمی را تغییر دهد). این یک تکرار توجیه‌پذیر است، نه نقض نرمال‌سازی.

### 🧰 وسایل مورد نیاز
PostgreSQL 18 (Docker)، `psql` یا pgAdmin، ابزار رسم ER.

### 📝 مراحل انجام کار
1. PostgreSQL را اجرا کنید و با `psql` وصل شوید. `SELECT version();` را اجرا کنید.
2. دیتابیس `shopdb` را بسازید و متصل شوید (`CREATE DATABASE shopdb;` و `\c shopdb`).
3. Schema زیر را در `sql/lab01.sql` ذخیره و اجرا کنید (این Schema پایه همه آزمایش‌هاست):

```sql
CREATE TABLE categories (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name      text NOT NULL UNIQUE,
  parent_id bigint REFERENCES categories(id)
);
CREATE TABLE customers (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL,
  email      text NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE products (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  category_id bigint NOT NULL REFERENCES categories(id),
  name        text NOT NULL,
  price       numeric(10,2) NOT NULL CHECK (price >= 0),
  stock       integer NOT NULL DEFAULT 0 CHECK (stock >= 0)
);
CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id),
  order_date  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE order_items (
  order_id   bigint  NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id bigint  NOT NULL REFERENCES products(id),
  quantity   integer NOT NULL CHECK (quantity > 0),
  unit_price numeric(10,2) NOT NULL CHECK (unit_price >= 0),
  PRIMARY KEY (order_id, product_id)
);
```

4. با `\d+ orders` و `\dt` ساختار را بررسی کنید و خروجی را در گزارش بگذارید.
5. نمودار ER را از روی Schema واقعی رسم کنید و با نمودار پیش‌گزارش مقایسه کنید. تفاوت‌ها را توضیح دهید.
6. وابستگی‌های تابعی هر جدول را بنویسید و نشان دهید Schema در 3NF است.
7. هر قید را با یک درج **نامعتبر** تست کنید (قیمت منفی، ایمیل تکراری، سفارش برای مشتری ناموجود) و پیام خطا را ثبت کنید.
8. با `pg_dump --schema-only shopdb > sql/schema_dump.sql` Schema را استخراج کنید.

### 📦 تحویلی‌ها
`lab01.sql`، نمودار ER، جدول وابستگی‌های تابعی، جدول آزمون قیدها (درج نامعتبر ← خطای مشاهده‌شده).

### ⚠️ خطاهای رایج
- استفاده از `float` برای پول (خطای گرد کردن).
- ذخیره مبلغ کل در `orders` و نگه‌داری دستی آن.
- نبودن قید `NOT NULL`/`CHECK` و اتکا به برنامه.

### 💡 مثال کاربردی
Schema خوب پایه هر پروژه تجارت الکترونیک است. قیدهای دیتابیس آخرین خط دفاع در برابر باگ برنامه و داده نادرست‌اند و برخلاف کد برنامه، دور زده نمی‌شوند.

### 🧪 تمرین افزوده
جدول `reviews (id, product_id, customer_id, rating, comment)` را اضافه کنید. چه کلیدهای خارجی و قیدی لازم است (مثلاً `rating` بین ۱ و ۵)؟ چگونه از دو نظر برای یک محصول از یک مشتری جلوگیری می‌کنید؟

## 🔬 آزمایش ۲: نرمال‌سازی و یکپارچگی داده

### 🎯 هدف
تحلیل وابستگی‌های تابعی، تجزیه یک جدول نرمال‌نشده تا 3NF/BCNF و استفاده از قیدها برای تضمین یکپارچگی.

### 📋 پیش‌گزارش
1. جدول زیر را در نظر بگیرید: `enrollment(student_id, student_name, course_id, course_title, instructor, instructor_office, grade)` با فرض: هر درس یک استاد دارد و هر استاد یک دفتر دارد. وابستگی‌های تابعی را بنویسید.
2. کلید کاندید را بیابید و بگویید جدول در کدام فرم نرمال است و چرا.
3. ناهنجاری‌های درج، حذف و به‌روزرسانی را با مثال نشان دهید.

### 📚 تئوری
- 1NF: مقادیر اتمی. 2NF: عدم وابستگی جزئی به کلید. 3NF: عدم وابستگی انتقالی. BCNF: هر دترمینان یک ابرکلید باشد.
- تجزیه باید **بدون‌اتلاف** (lossless join) و ترجیحاً **حافظ وابستگی** باشد.
- قیدها: `PRIMARY KEY`، `UNIQUE`، `FOREIGN KEY` با `ON DELETE/UPDATE` (`RESTRICT`، `CASCADE`، `SET NULL`)، `CHECK`، `EXCLUDE`.
- نرمال‌سازی کامل همیشه بهترین نیست؛ در گزارش‌گیری سنگین گاهی **نرمال‌زدایی هدفمند** (با مستندسازی دلیل) پذیرفته است.

### 🧰 وسایل مورد نیاز
`psql`، دیتابیس جدا برای این آزمایش (`CREATE DATABASE normlab;`).

### 📝 مراحل انجام کار
1. جدول نرمال‌نشده `enrollment` را بسازید و چند ردیف نمونه وارد کنید که ناهنجاری‌ها را نشان دهد.
2. ناهنجاری به‌روزرسانی را اجرا کنید: دفتر یک استاد را تغییر دهید و ناسازگاری ایجاد‌شده را نشان دهید.
3. جدول را تا 3NF (و BCNF در صورت امکان) تجزیه کنید و Schema جدید را با کلیدهای خارجی بسازید.
4. با یک `JOIN` جدول اصلی را بازسازی کنید و نشان دهید هیچ ردیفی اضافه یا گم نشده است (مقایسه با `EXCEPT` در هر دو جهت).
5. آزمون‌های قید: ثبت‌نام برای درس ناموجود (FK)، نمره خارج از بازه (CHECK)، ثبت‌نام تکراری (PK).
6. رفتار `ON DELETE RESTRICT` و `ON DELETE CASCADE` را با حذف یک استاد/درس مقایسه کنید و مناسب‌ترین گزینه برای هر رابطه را بنویسید.
7. یک مثال نرمال‌زدایی هدفمند ارائه کنید (مثلاً نگهداری `unit_price` در `order_items`) و توجیه کنید.

### 📦 تحویلی‌ها
فهرست وابستگی‌های تابعی و فرم نرمال، Schema قبل و بعد، اثبات بازسازی بدون‌اتلاف، نتایج آزمون قیدها.

### ⚠️ خطاهای رایج
- تجزیه‌ای که اطلاعات را از دست می‌دهد (lossy).
- استفاده از `CASCADE` بدون فکر روی داده مالی.
- نگرفتن کلید کاندید درست.

### 💡 مثال کاربردی
نبود نرمال‌سازی منجر به ناسازگاری (یک استاد با دو دفتر متفاوت در دو ردیف) می‌شود. در سیستم‌های واقعی چنین خطاهایی گزارش‌های مالی و آماری را نادرست می‌کنند.

### 🧪 تمرین افزوده
با ستون بازه زمانی (`daterange`) و قید `EXCLUDE USING gist` از هم‌پوشانی رزرو یک اتاق در یک بازه جلوگیری کنید (نیاز به افزونه `btree_gist`). در PostgreSQL 18 قیدهای زمانی (`WITHOUT OVERLAPS`) را هم بررسی کنید.

## 🔬 آزمایش ۳: کوئری‌های پایه و داده نمونه

### 🎯 هدف
تولید داده نمونه **بازتولیدپذیر و حجیم**، و نوشتن کوئری‌های `SELECT`، `WHERE`، `ORDER BY`، `GROUP BY`، `HAVING` و توابع تجمعی با درک رفتار `NULL`.

### 📋 پیش‌گزارش
1. تفاوت `COUNT(*)` و `COUNT(col)` و رفتار `AVG` با `NULL` را بنویسید.
2. توضیح دهید چرا `LIMIT` بدون `ORDER BY` نتیجه نامعین دارد.
3. ترتیب منطقی اجرای یک SELECT (`FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`) را بنویسید و بگویید چرا نمی‌توان در `WHERE` از نام مستعار ستون استفاده کرد.

### 📚 تئوری
- `GROUP BY` ردیف‌ها را گروه‌بندی می‌کند و `HAVING` گروه‌ها را فیلتر می‌کند (برخلاف `WHERE` که ردیف‌ها را).
- `date_trunc('month', ts)` برای گروه‌بندی زمانی.
- `FETCH FIRST n ROWS WITH TIES` رتبه‌های مساوی آخر را هم می‌آورد.
- **داده کم** (مثل ۱۰ ردیف) آموزنده نیست: بهینه‌ساز روی جدول کوچک همیشه Seq Scan انتخاب می‌کند.

### 🧰 وسایل مورد نیاز
دیتابیس `shopdb` با Schema آزمایش ۱.

### 📝 مراحل انجام کار
1. داده نمونه را با اسکریپت زیر وارد کنید (`sql/seed.sql`). `setseed` باعث می‌شود همه دانشجویان داده یکسان بسازند. حدود ۱۰۰ هزار سفارش و ۲۰۰ هزار قلم ایجاد می‌شود. ۵۰ مشتری عمداً هیچ سفارشی ندارند و ۲۰ محصول عمداً فروخته نشده‌اند.

```sql
SELECT setseed(0.42);
INSERT INTO categories(name, parent_id) VALUES
  ('Electronics', NULL), ('Books', NULL), ('Home', NULL);
INSERT INTO categories(name, parent_id) VALUES
  ('Phones', 1), ('Laptops', 1), ('Novels', 2);
INSERT INTO customers(name, email, created_at)
SELECT 'Customer ' || g, 'user' || g || '@example.com',
       now() - random() * interval '730 days'
FROM generate_series(1, 1000) AS g;
INSERT INTO products(category_id, name, price, stock)
SELECT 1 + floor(random() * 6)::int, 'Product ' || g,
       round((5 + random() * 495)::numeric, 2), floor(random() * 200)::int
FROM generate_series(1, 500) AS g;

SELECT 1 + floor(random() * 950)::int,
       now() - random() * interval '365 days'
FROM generate_series(1, 100000);
INSERT INTO order_items(order_id, product_id, quantity, unit_price)
SELECT o.id, p.id, 1 + floor(random() * 3)::int, p.price
FROM orders o
JOIN LATERAL generate_series(1, 1 + (o.id % 3)::int) AS k ON true
JOIN products p ON p.id = 1 + ((o.id * 7 + k * 13) % 480);
ANALYZE;
```

> برای اجرای مجدد از صفر ابتدا: `TRUNCATE order_items, orders, products, customers, categories RESTART IDENTITY CASCADE;`

2. تعداد ردیف هر جدول را بشمارید و گزارش کنید.
3. کوئری‌های زیر را بنویسید، اجرا کنید و خروجی را ثبت کنید:
   - محصولات با قیمت بیش از ۱۰۰ دلار (به ترتیب قیمت)
   - ۵ مشتری با بیشترین تعداد سفارش (با `WITH TIES` و ترتیب ثابت برای تساوی)
   - مجموع فروش هر ماه (با `date_trunc` و جمع `quantity × unit_price`)
   - میانگین قیمت محصولات هر دسته
   - دسته‌هایی که میانگین قیمتشان بیش از ۲۵۰ است (`HAVING`)
4. با `\timing` زمان هر کوئری را بگیرید (۳ تکرار، میانه).
5. برای هر کوئری `EXPLAIN` بگیرید و نوع Scan را ثبت کنید. توضیح دهید چرا Seq Scan انتخاب شده است.
6. یک کوئری بنویسید که رفتار `NULL` را نشان دهد (مثلاً مقایسه `= NULL` و `IS NULL`).

### 📦 تحویلی‌ها
`seed.sql`، شمارش ردیف‌ها، خروجی و زمان هر کوئری، تحلیل نوع Scan.

### ⚠️ خطاهای رایج
- `WHERE x = NULL` به‌جای `IS NULL`.
- `LIMIT` بدون `ORDER BY`.
- استفاده از `HAVING` برای شرطی که باید در `WHERE` باشد (کندتر).

### 💡 مثال کاربردی
کوئری‌های تجمعی ماهانه پایه داشبورد فروش‌اند. در سیستم واقعی این کوئری‌ها روی میلیون‌ها ردیف اجرا می‌شوند و کوچک‌ترین ناکارآمدی هزینه دارد.

### 🧪 تمرین افزوده
مشتریانی را بیابید که هیچ سفارشی ندارند (باید ۵۰ مورد باشد) و صحت شمارش را با دو روش مختلف تأیید کنید.

## 🔬 آزمایش ۴: JOIN و زیرکوئری‌ها

### 🎯 هدف
تسلط بر انواع JOIN، الگوی anti-join، زیرکوئری‌ها و `LATERAL`، و مقایسه الگوریتم‌های اجرای JOIN.

### 📋 پیش‌گزارش
1. با دیاگرام ون تفاوت INNER، LEFT، RIGHT، FULL و CROSS JOIN را نشان دهید.
2. توضیح دهید چرا `NOT IN (زیرکوئری)` در حضور `NULL` نتیجه غلط می‌دهد و چرا `NOT EXISTS` ایمن است.
3. سه الگوریتم JOIN را معرفی کنید: Nested Loop، Hash Join، Merge Join و بگویید هرکدام برای چه حالتی مناسب است.

### 📚 تئوری
- `LEFT JOIN ... WHERE right.id IS NULL` یکی از الگوهای anti-join است. `NOT EXISTS` معادل و معمولاً به همان اندازه کارآمد است.
- زیرکوئری مرتبط (correlated) از نظر مفهومی برای هر ردیف اجرا می‌شود، اما بهینه‌ساز PostgreSQL اغلب آن را به join تبدیل می‌کند (مثلاً `EXISTS` به semi-join). پس «همیشه کند است» دقیق نیست و باید **اندازه‌گیری کرد**.
- `LATERAL` اجازه می‌دهد زیرکوئری به ستون‌های جدول قبلی در `FROM` ارجاع دهد (مناسب «آخرین N رکورد هر گروه»).
- `DISTINCT ON (col)` اولین ردیف هر گروه را (طبق `ORDER BY`) برمی‌گرداند و مخصوص PostgreSQL است.

### 🧰 وسایل مورد نیاز
دیتابیس `shopdb` با داده آزمایش ۳.

### 📝 مراحل انجام کار
1. نام هر مشتری و تعداد سفارش‌هایش را نمایش دهید (`LEFT JOIN`؛ مشتریان بدون سفارش باید با ۰ بیایند).
2. محصولاتی که هرگز فروخته نشده‌اند را با سه روش بیابید: `LEFT JOIN ... IS NULL`، `NOT EXISTS` و `NOT IN`. نتیجه و زمان هر سه را مقایسه کنید (باید ۲۰ محصول باشد).
3. مشتریانی که بیش از **میانگین** تعداد سفارش‌ها سفارش داده‌اند را با زیرکوئری و سپس با `JOIN + GROUP BY` بنویسید. `EXPLAIN (ANALYZE, BUFFERS)` هر دو را مقایسه کنید.
4. آخرین سفارش هر مشتری را با سه روش بنویسید: زیرکوئری مرتبط، `DISTINCT ON` و `LATERAL ... ORDER BY ... LIMIT 1`. زمان و طرح اجرا را مقایسه کنید.
5. **الگوریتم JOIN:** یک کوئری سه‌جدولی بنویسید (`customers ⋈ orders ⋈ order_items`). در طرح اجرا نوع JOIN انتخاب‌شده را ثبت کنید. سپس موقتاً با `SET enable_hashjoin = off;` (و در جلسه جداگانه `enable_mergejoin = off`) الگوریتم را عوض کنید و تغییر زمان را اندازه بگیرید. تنظیمات را `RESET` کنید.
6. یک `FULL JOIN` و یک `CROSS JOIN` معنادار بنویسید (مثلاً همه ترکیب‌های دسته × ماه) و کاربرد هرکدام را توضیح دهید.

### 📦 تحویلی‌ها
کوئری‌ها، جدول زمان‌ها و طرح‌های اجرا (سه روش anti-join، سه روش آخرین سفارش، سه الگوریتم JOIN) و تحلیل.

### ⚠️ خطاهای رایج
- `NOT IN` روی ستون دارای `NULL`.
- فراموش‌کردن شرط JOIN (ضرب دکارتی ناخواسته).
- شرط روی جدول سمت راست `LEFT JOIN` در `WHERE` که آن را عملاً به INNER JOIN تبدیل می‌کند (باید در `ON` باشد).

### 💡 مثال کاربردی
«مشتریان بدون خرید» برای کمپین بازگشت و «محصولات بدون فروش» برای تخفیف‌گذاری استفاده می‌شوند. انتخاب بین زیرکوئری و JOIN با اندازه‌گیری انجام می‌شود، نه با حدس.

### 🧪 تمرین افزوده
پرفروش‌ترین محصول هر ماه را بیابید و نتیجه را با نسخه `DISTINCT ON` و نسخه `ROW_NUMBER()` مقایسه کنید.

## 🔬 آزمایش ۵: ایندکس‌گذاری و بهینه‌سازی

### 🎯 هدف
خواندن طرح اجرا، ساخت ایندکس‌های مناسب (B-tree، چندستونه، covering، جزئی، عبارتی، GIN) و **اندازه‌گیری** اثر آن‌ها روی خواندن و نوشتن.

### 📋 پیش‌گزارش
1. اجزای خروجی `EXPLAIN` را توضیح دهید (cost، rows، actual time، loops، Buffers).
2. توضیح دهید چرا ترتیب ستون‌ها در ایندکس چندستونه مهم است (قاعده پیشوند چپ‌ترین).
3. پیش‌بینی کنید برای هر کوئری بخش ۳ چه نوع Scan انتخاب می‌شود و چرا.

### 📚 تئوری
- ایندکس خواندن را سریع و نوشتن را کند می‌کند و فضا می‌گیرد. هر ایندکس باید با اندازه‌گیری توجیه شود.
- انواع: B-tree (پیش‌فرض)، Hash، GIN (جستجوی متن/آرایه/JSONB)، GiST، BRIN (داده مرتب‌شده بزرگ).
- انواع Scan: Seq Scan، Index Scan، Index Only Scan (نیازمند نقشه دید به‌روز، یعنی `VACUUM`)، Bitmap Scan.
- بهینه‌ساز **مبتنی بر هزینه** است: برای شرط غیر‌گزینشی (مثلاً ۴۰٪ ردیف‌ها) حتی با وجود ایندکس Seq Scan انتخاب می‌کند و درست هم هست.
- پس از بارگذاری انبوه داده باید `ANALYZE` اجرا شود تا آمار به‌روز باشد.
- PostgreSQL 18: Skip Scan اجازه می‌دهد ایندکس چندستونه حتی وقتی شرط روی ستون پیشوندی نیست استفاده شود (مؤثرتر وقتی ستون پیشوندی مقادیر متمایز کمی دارد).
- شرط یک **ایندکس جزئی** باید با توابع `IMMUTABLE` نوشته شود؛ استفاده از `now()` در شرط خطا می‌دهد.

### 🧰 وسایل مورد نیاز
دیتابیس `shopdb` با داده حجیم آزمایش ۳. افزونه `pg_trgm`.

### 📝 مراحل انجام کار
1. کوئری «تعداد سفارش‌های ۲ روز اخیر» را بنویسید و `EXPLAIN (ANALYZE, BUFFERS)` آن را (۳ بار) ثبت کنید.
2. `CREATE INDEX idx_orders_date ON orders(order_date);` را بسازید، `ANALYZE` بزنید و دوباره اندازه بگیرید. تغییر نوع Scan و زمان را تحلیل کنید.
3. حجم ایندکس را با `pg_relation_size('idx_orders_date')` گزارش کنید.
4. ایندکس چندستونه `(customer_id, order_date)` بسازید. کوئری «سفارش‌های یک مشتری در ۳۰ روز اخیر» را تست کنید. سپس کوئری‌ای که فقط روی `order_date` شرط دارد را روی همین ایندکس تست کنید و نتیجه را توضیح دهید.
5. **Covering index:** با `INCLUDE (id)` ایندکسی بسازید که کوئری را به `Index Only Scan` تبدیل کند. اگر Heap Fetches صفر نشد، `VACUUM` بزنید و دلیل را توضیح دهید.
6. **ایندکس عبارتی:** برای جستجوی `lower(email) = '...'` ایندکس عبارتی بسازید.
7. **ایندکس جزئی:** یک ایندکس جزئی با شرط ثابت بسازید (مثلاً فقط محصولات با `stock = 0`). چرا شرط با `now()` خطا می‌دهد؟
8. **جستجوی متنی:** جدول `products` فقط ۵۰۰ ردیف دارد و بهینه‌ساز از ایندکس trigram استفاده نمی‌کند. جدولی با ۲۰۰ هزار نام تصادفی بسازید (`generate_series` و `md5`)، `LIKE '%...%'` را قبل و بعد از `CREATE INDEX ... USING gin (name gin_trgm_ops)` مقایسه کنید.
9. **هزینه نوشتن:** درج ۱۰۰ هزار ردیف در یک جدول کپی را با ۰، ۲ و ۵ ایندکس زمان‌گیری کنید و نمودار بکشید.
10. با `pg_stat_user_indexes` ایندکس‌های بلااستفاده را بیابید (ستون `idx_scan`).
11. با `DROP INDEX` ایندکس‌ها را حذف و اثر را ثبت کنید.
12. (اختیاری، PostgreSQL 18) برای دیدن Skip Scan، ایندکسی با پیشوند کم‌مقدار (مثلاً `products(category_id, price)`) بسازید و کوئری فقط روی `price` را بزنید. خط `Index Searches` در طرح اجرا را بررسی کنید.

### 📦 تحویلی‌ها
جدول زمان و نوع Scan قبل و بعد از هر ایندکس، حجم ایندکس‌ها، نمودار هزینه نوشتن، تحلیل.

### ⚠️ خطاهای رایج
- نزدن `ANALYZE` پس از بارگذاری و قضاوت بر اساس آمار کهنه.
- ساخت ایندکس روی ستونی با گزینش‌پذیری پایین و تعجب از بی‌استفاده بودن.
- اندازه‌گیری فقط یک‌بار (کش سرد در برابر گرم).

### 💡 مثال کاربردی
جستجوی سفارش‌های یک بازه زمانی در جدول چندمیلیونی بدون ایندکس ثانیه‌ها یا دقیقه‌ها طول می‌کشد و با ایندکس مناسب به میلی‌ثانیه می‌رسد. ایندکس اضافه اما سرعت درج را کم و حافظه را هدر می‌دهد.

### 🧪 تمرین افزوده
ایندکس `orders.order_date` را با یک ایندکس BRIN مقایسه کنید (اندازه و سرعت) و بگویید BRIN کی مناسب است.

## 🔬 آزمایش ۶: توابع پنجره‌ای (Window Functions)

### 🎯 هدف
استفاده از `ROW_NUMBER`، `RANK`، `DENSE_RANK`، `LAG`، `LEAD`، توابع تجمعی پنجره‌ای و فریم‌ها برای تحلیل داده.

### 📋 پیش‌گزارش
1. تفاوت `GROUP BY` و تابع پنجره‌ای را (حفظ تعداد ردیف‌ها) توضیح دهید.
2. برای مجموعه امتیازات {۹۰، ۸۵، ۸۵، ۸۰} خروجی `ROW_NUMBER`، `RANK` و `DENSE_RANK` را دستی بنویسید.
3. توضیح دهید چرا نمی‌توان تابع پنجره‌ای را مستقیم در `WHERE` گذاشت و راه‌حل چیست.

### 📚 تئوری
- توابع پنجره‌ای **بعد از** `WHERE` و `GROUP BY` اجرا می‌شوند. برای فیلتر روی نتیجه آن‌ها از زیرکوئری یا CTE استفاده کنید.
- `PARTITION BY` پنجره را گروه‌بندی و `ORDER BY` درون پنجره ترتیب می‌دهد.
- فریم: `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` (بر اساس تعداد ردیف) در برابر `RANGE` (بر اساس مقدار).
- `NTILE(n)`، `SUM() OVER (ORDER BY ...)` برای جمع تجمعی.

### 🧰 وسایل مورد نیاز
دیتابیس `shopdb`.

### 📝 مراحل انجام کار
1. برای هر مشتری سفارش‌هایش را به ترتیب تاریخ (نزولی) شماره‌گذاری کنید (`ROW_NUMBER`).
2. رتبه محصولات بر اساس مجموع فروش را با `RANK` و `DENSE_RANK` بگیرید و تفاوت را روی حالت‌های مساوی نشان دهید.
3. فروش ماهانه را حساب کنید و در همان کوئری فروش ماه قبل (`LAG`) و درصد رشد را نمایش دهید.
4. میانگین متحرک ۳ ماهه فروش را با فریم `ROWS` محاسبه کنید. توجه کنید اگر ماهی بدون فروش وجود داشته باشد فریم `ROWS` ماه‌ها را نادیده می‌گیرد؛ با `generate_series` ماه‌های خالی را پر کنید.
5. فروش تجمعی (`SUM() OVER`) و سهم هر ماه از کل سال را حساب کنید.
6. پرفروش‌ترین محصول **هر دسته** را با `ROW_NUMBER` در زیرکوئری بیابید (باید ۶ سطر باشد).
7. مشتریان را با `NTILE(4)` به چهار گروه خرید تقسیم کنید.
8. `EXPLAIN (ANALYZE, BUFFERS)` یکی از کوئری‌ها را بررسی کنید و گره `WindowAgg` و مرتب‌سازی را شناسایی کنید.

### 📦 تحویلی‌ها
کوئری‌ها و خروجی‌ها، جدول مقایسه `RANK`/`DENSE_RANK`، تحلیل طرح اجرا.

### ⚠️ خطاهای رایج
- فراموش کردن `ORDER BY` درون `OVER` (نتیجه نامعین یا غیر‌مورد‌انتظار).
- اشتباه بین `ROWS` و `RANGE`.
- فرض اینکه ماه‌های بدون داده در خروجی ظاهر می‌شوند.

### 💡 مثال کاربردی
تحلیل روند فروش، رتبه‌بندی مشتریان، محاسبه رشد دوره‌ای و میانگین متحرک در داشبوردهای BI از همین توابع استفاده می‌کنند.

### 🧪 تمرین افزوده
با `ROLLUP` یا `GROUPING SETS` فروش را به‌صورت هم‌زمان بر حسب (دسته، ماه)، (دسته) و (کل) بگیرید.

## 🔬 آزمایش ۷: Viewها، Materialized View و CTE

### 🎯 هدف
ساده‌سازی کوئری‌های پیچیده با View و CTE، آشنایی با Materialized View و تفاوت‌های عملکردی و امنیتی آن‌ها.

### 📋 پیش‌گزارش
1. تفاوت View و Materialized View را از نظر ذخیره داده و تازگی بنویسید.
2. توضیح دهید CTE از PostgreSQL 12 به بعد چه زمانی درون‌خطی (inline) می‌شود.
3. یک نمونه ساختار درختی (دسته‌بندی) را با بازگشتی مدل کنید و شرط توقف را بنویسید.

### 📚 تئوری
- View یک کوئری ذخیره‌شده است؛ هنگام استفاده به کوئری اصلی بازنویسی می‌شود و داده ذخیره نمی‌کند.
- پیش‌فرض، View با **مجوزهای مالکش** اجرا می‌شود. گزینه `WITH (security_invoker = true)` آن را با مجوزهای کاربر فراخوان (و در نتیجه RLS او) اجرا می‌کند.
- Materialized View نتیجه را ذخیره می‌کند و با `REFRESH MATERIALIZED VIEW` تازه می‌شود. `REFRESH ... CONCURRENTLY` بدون قفل‌کردن خواننده‌ها کار می‌کند و به یک ایندکس یکتا نیاز دارد.
- CTE غیربازگشتی که یک‌بار ارجاع شود معمولاً درون‌خطی می‌شود. با `MATERIALIZED`/`NOT MATERIALIZED` می‌توان کنترل کرد.
- CTE بازگشتی (`WITH RECURSIVE`) برای درخت و گراف است. در داده دارای حلقه به `CYCLE` یا شمارنده عمق نیاز دارد.

### 🧰 وسایل مورد نیاز
دیتابیس `shopdb` (جدول `categories` دارای `parent_id`).

### 📝 مراحل انجام کار
1. View `order_summary` بسازید: شناسه سفارش، نام مشتری، تعداد اقلام، مبلغ کل. از آن با `SELECT` استفاده کنید و `EXPLAIN` بگیرید تا بازنویسی View دیده شود.
2. نسخه `security_invoker` را بسازید و در آزمایش ۱۰ اثر آن را روی RLS بسنجید.
3. با CTE مجموع خرید هر مشتری را حساب کنید و ۱۰ مشتری برتر را فیلتر کنید.
4. با CTE بازگشتی مسیر کامل هر دسته (`Electronics > Phones`) را تولید کنید.
5. Materialized View `monthly_sales` بسازید، ایندکس یکتا روی ماه بگذارید و `REFRESH ... CONCURRENTLY` را اجرا کنید.
6. **سنجش:** کوئری فروش ماهانه را مستقیم روی جداول و روی Materialized View زمان‌گیری کنید. سپس چند سفارش جدید درج کنید و نشان دهید Materialized View تا `REFRESH` کهنه است.
7. با `CREATE OR REPLACE VIEW` تعریف View را به‌روز کنید و محدودیت‌های آن (تغییر ترتیب/نوع ستون) را ثبت کنید.
8. View ساده‌ای بسازید که به‌روزرسانی‌پذیر باشد و با `WITH CHECK OPTION` درج ردیف خارج از شرط View را رد کند.

### 📦 تحویلی‌ها
تعریف View ها و Materialized View، خروجی‌ها، جدول زمان (مستقیم در برابر Materialized)، نمایش کهنگی داده.

### ⚠️ خطاهای رایج
- فرض اینکه Materialized View خودکار به‌روز می‌شود.
- حلقه بی‌پایان در CTE بازگشتی.
- فرض اینکه View همیشه از دسترسی کاربر محافظت می‌کند (پیش‌فرض با مجوز مالک اجرا می‌شود).

### 💡 مثال کاربردی
Materialized View برای داشبوردهای سنگین که تازگی لحظه‌ای لازم ندارند (گزارش شبانه) ایده‌آل است. CTE بازگشتی برای ساختار سازمانی و دسته‌بندی‌های تودرتو ضروری است.

### 🧪 تمرین افزوده
View ای بسازید که فقط محصولات فعال (`stock > 0`) را نشان دهد و با آن ارزش کل موجودی را حساب کنید.

## 🔬 آزمایش ۸: تراکنش‌ها و کنترل همزمانی

### 🎯 هدف
درک ACID، MVCC و سطوح Isolation در PostgreSQL با مشاهده عملی ناهنجاری‌های همزمانی و روش‌های مقابله.

### 📋 پیش‌گزارش
1. چهار ویژگی ACID را با مثال انتقال وجه توضیح دهید.
2. جدول سطوح Isolation را بنویسید: کدام ناهنجاری (dirty read، non-repeatable read، phantom، write skew) در هر سطح مجاز است؟ در PostgreSQL `READ UNCOMMITTED` عملاً چه رفتاری دارد؟
3. پیش‌بینی کنید هر سناریوی بخش ۳ چه نتیجه‌ای می‌دهد.

### 📚 تئوری
- PostgreSQL از **MVCC** استفاده می‌کند: خواننده‌ها نویسنده‌ها را مسدود نمی‌کنند. نویسنده‌ها فقط نویسنده‌های همان ردیف را مسدود می‌کنند.
- `READ COMMITTED` (پیش‌فرض): هر دستور یک snapshot تازه می‌بیند. `REPEATABLE READ`: یک snapshot برای کل تراکنش (در PostgreSQL phantom هم رخ نمی‌دهد). `SERIALIZABLE`: ایزولاسیون سریالی با تشخیص تعارض (SSI)؛ ممکن است با خطای `40001` شکست بخورد و **برنامه باید تراکنش را دوباره تلاش کند**.
- `SELECT ... FOR UPDATE` ردیف را قفل می‌کند. `SKIP LOCKED` برای صف‌های کار و `NOWAIT` برای شکست فوری.
- بن‌بست (deadlock) توسط PostgreSQL تشخیص داده و یکی از تراکنش‌ها با خطای `40P01` لغو می‌شود.
- DDL در PostgreSQL تراکنشی است (قابل `ROLLBACK`).
- هر ردیف ستون‌های سیستمی `xmin`/`xmax` دارد؛ `VACUUM` نسخه‌های مرده را پاک می‌کند.

### 🧰 وسایل مورد نیاز
دیتابیس `shopdb`، **دو (یا سه) ترمینال `psql` جدا**، جدول `accounts (id, balance CHECK (balance >= 0))` با دو حساب نمونه.

### 📝 مراحل انجام کار
1. **اتمی‌بودن:** تراکنشی با `BEGIN` شروع کنید، سفارشی درج کنید، `ROLLBACK` بزنید و عدم ثبت را نشان دهید. با `COMMIT` ثبت را تأیید کنید. نشان دهید DDL هم قابل `ROLLBACK` است.
2. **عدم مسدودسازی خواننده:** در ترمینال ۱ موجودی یک محصول را کم کنید (بدون `COMMIT`). در ترمینال ۲ همان ردیف را بخوانید و بنویسید چه می‌بینید و چرا مسدود نمی‌شود. سپس در ترمینال ۲ همان ردیف را `UPDATE` کنید و رفتار را شرح دهید.
3. **ناهنجاری non-repeatable read:** در `READ COMMITTED` یک ردیف را دوبار در یک تراکنش بخوانید در حالی که تراکنش دیگری آن را تغییر و commit می‌کند. با `REPEATABLE READ` تکرار کنید.
4. **Lost update:** دو تراکنش هم‌زمان با الگوی «بخوان، در برنامه تغییر بده، بنویس» موجودی را به‌روزرسانی کنند. نتیجه غلط را نشان دهید. سه راه‌حل را آزمایش کنید: `UPDATE ... SET stock = stock - 1`، `SELECT ... FOR UPDATE` و سطح `REPEATABLE READ` (و خطای `40001`).
5. **Write skew:** دو پزشک آماده‌به‌کار (حداقل یک پزشک باید باقی بماند) هم‌زمان خود را از لیست خارج کنند. در `REPEATABLE READ` ناهنجاری و در `SERIALIZABLE` خطای `40001` را مشاهده کنید.
6. **بن‌بست:** دو تراکنش دو ردیف را با ترتیب معکوس قفل کنند. خطای `40P01` را ثبت کنید و با ترتیب ثابت قفل‌گیری مشکل را رفع کنید.
7. با `pg_stat_activity` و `pg_locks` یک تراکنش منتظر قفل را شناسایی کنید. `lock_timeout` را تنظیم و اثرش را ببینید.
8. `SAVEPOINT`: عملیاتی انجام دهید، به SAVEPOINT برگردید و ادامه دهید.
9. **انتقال وجه:** با تراکنش و قید `CHECK (balance >= 0)` ثابت کنید در انتقال بیش از موجودی، هیچ تغییری باقی نمی‌ماند.
10. (اختیاری) با `pgbench` و یک اسکریپت سفارشی، مقایسه کنید که TPS با افزایش تعداد کلاینت‌هایی که روی یک ردیف می‌نویسند چگونه تغییر می‌کند.

### 📦 تحویلی‌ها
لاگ هر سناریو (دو ترمینال کنار هم، با برچسب زمانی ترتیب فرمان‌ها)، جدول ناهنجاری × سطح Isolation مشاهده‌شده، کد منطق تلاش مجدد برای `40001`.

### ⚠️ خطاهای رایج
- باز گذاشتن تراکنش (`idle in transaction`) که قفل نگه می‌دارد و `VACUUM` را مختل می‌کند.
- ننوشتن منطق تلاش مجدد برای شکست‌های سریال‌پذیری.
- فرض اینکه در PostgreSQL dirty read ممکن است.

### 💡 مثال کاربردی
در فروشگاه، «کاهش موجودی» و «ثبت سفارش» باید اتمی باشند و فروش بیش از موجودی نباید رخ دهد. در بانکداری انتقال وجه بدون کنترل همزمانی منجر به ناسازگاری مالی می‌شود.

### 🧪 تمرین افزوده
با `FOR UPDATE SKIP LOCKED` یک صف کار ساده بسازید که چند Worker هم‌زمان ردیف‌ها را بدون برخورد بردارند.

## 🔬 آزمایش ۹: توابع، رویه‌ها و تریگرها (PL/pgSQL)

### 🎯 هدف
پیاده‌سازی منطق تجاری در سمت دیتابیس با توابع، رویه‌ها و تریگرها همراه با مدیریت صحیح خطا و تراکنش.

### 📋 پیش‌گزارش
1. تفاوت `FUNCTION` و `PROCEDURE` و ویژگی‌های `IMMUTABLE`/`STABLE`/`VOLATILE` را بنویسید.
2. توضیح دهید چرا الگوی `UPDATE products SET stock = stock - q WHERE id = ... AND stock >= q` از «خواندن موجودی و سپس نوشتن» ایمن‌تر است.
3. تفاوت تریگر سطح ردیف (`FOR EACH ROW`) و سطح دستور، و `BEFORE`/`AFTER` را بنویسید.

### 📚 تئوری
- PL/pgSQL زبان رویه‌ای PostgreSQL با شرط، حلقه، متغیر و مدیریت خطاست.
- **رویه** (`CALL`) می‌تواند `COMMIT`/`ROLLBACK` انجام دهد، اما نه داخل بلوکی که `EXCEPTION` دارد و نه وقتی از داخل یک تراکنش صریح فراخوانی شده باشد. **تابع** نمی‌تواند تراکنش را کنترل کند.
- وقتی خطا `RAISE EXCEPTION` می‌شود، کل تراکنش (یا زیرتراکنش بلوک `EXCEPTION`) خودکار لغو می‌شود. معمولاً `ROLLBACK` صریح لازم نیست.
- متغیر ویژه `FOUND` و `GET DIAGNOSTICS ... ROW_COUNT` نتیجه آخرین دستور را نشان می‌دهند.
- تریگر: تابعی با `RETURNS trigger` که از `NEW` و `OLD` استفاده می‌کند.
- `SECURITY DEFINER` با مجوز مالک اجرا می‌شود و باید حتماً `SET search_path` ثابت داشته باشد (امنیت).
- `EXPLAIN` داخل بدنه توابع PL/pgSQL را نشان نمی‌دهد؛ برای آن از `auto_explain` با `log_nested_statements` استفاده می‌شود.

### 🧰 وسایل مورد نیاز
دیتابیس `shopdb`، جدول `price_history`، (اختیاری) pgTAP.

### 📝 مراحل انجام کار
1. تابع `customer_total(customer_id)` بنویسید که مجموع خرید یک مشتری را برگرداند (`STABLE`). در یک `SELECT` روی چند مشتری استفاده کنید.
2. رویه `place_order(customer_id, product_id, qty)` بنویسید که:
   - موجودی را **اتمی** و با شرط `stock >= qty` کم کند،
   - سفارش و قلم سفارش را با قیمت لحظه درج کند،
   - در موجودی ناکافی با پیام و کد خطای مناسب `RAISE EXCEPTION` کند.
3. رویه را با سناریوی موفق و ناموفق (از `psql` و از داخل `DO` با گرفتن خطا) تست کنید و نشان دهید در شکست هیچ تغییری باقی نمی‌ماند.
4. تابع `RETURNS TABLE` بنویسید که محصولات با موجودی زیر آستانه را برگرداند.
5. تریگر `AFTER UPDATE OF price` بنویسید که تغییر قیمت (قدیم و جدید و زمان) را در `price_history` ثبت کند و فقط وقتی قیمت واقعاً تغییر کرده است.
6. **هشدار طراحی:** اگر رویه موجودی را کم می‌کند، تریگر کاهش موجودی روی `order_items` موجودی را دوباره کم می‌کند. یکی را انتخاب کنید، دلیل بنویسید و نشان دهید با هر دو چه می‌شود.
7. آزمون ضد-نمونه: با تلاش همزمان ۲ ترمینال برای خرید آخرین واحد موجودی، ثابت کنید موجودی منفی نمی‌شود.
8. بخش بررسی عملکرد: با `auto_explain` یا با اندازه‌گیری زمان، هزینه فراخوانی تابع روی ۱۰۰ هزار ردیف را با معادل SQL خالص مقایسه کنید.
9. تست‌های خودکار: حداقل ۵ مورد (موفق، موجودی ناکافی، محصول ناموجود، کمیت منفی، تغییر قیمت) در یک فایل `sql/test_lab09.sql` که با خطا متوقف شود.

### 📦 تحویلی‌ها
کد توابع/رویه‌ها/تریگرها، فایل تست خودکار با نتیجه، مقایسه عملکرد، تحلیل تصمیم طراحی (مرحله ۶).

### ⚠️ خطاهای رایج
- استفاده از `ROLLBACK` درون بلوک دارای `EXCEPTION` در رویه.
- دوبار کاهش موجودی (رویه و تریگر).
- تریگری که خودش دوباره تریگر را فعال می‌کند (بازگشت).

### 💡 مثال کاربردی
رویه‌های ذخیره‌شده منطق تجاری را متمرکز می‌کنند و هر برنامه‌ای که به دیتابیس وصل می‌شود از آن استفاده می‌کند. تریگرها برای ثبت تاریخچه تغییرات (Audit) مناسب‌اند، ولی استفاده بیش‌ازحد باعث پنهان‌شدن منطق می‌شود.

### 🧪 تمرین افزوده
با `RETURNING OLD, NEW` (PostgreSQL 18) در یک `UPDATE`، قیمت قدیم و جدید را در همان دستور برگردانید و با تریگر مقایسه کنید.

## 🔬 آزمایش ۱۰: نقش‌ها، RLS و پشتیبان‌گیری

### 🎯 هدف
اعمال اصل **حداقل دسترسی** با نقش‌ها و مجوزها، امنیت سطح ردیف (RLS)، آشنایی با SQL Injection، و طراحی و **تأیید** پشتیبان‌گیری و بازیابی.

### 📋 پیش‌گزارش
1. اصل حداقل دسترسی را برای سه نقش (خواننده، نویسنده، مدیر) روی جداول `shopdb` طراحی کنید.
2. توضیح دهید چرا مالک جدول و `superuser` از RLS مستثنی هستند و `FORCE ROW LEVEL SECURITY` چه می‌کند.
3. تفاوت `pg_dump` (منطقی) و `pg_basebackup` (فیزیکی) و ایده PITR را بنویسید.

### 📚 تئوری
- نقش‌ها: `CREATE ROLE` (با `LOGIN` یا بدون). مجوزها با `GRANT`/`REVOKE` روی دیتابیس، schema، جدول و **sequence** داده می‌شوند.
- از PostgreSQL 15 به بعد کاربران عادی به‌طور پیش‌فرض اجازه ساختن شیء در schema `public` را ندارند.
- RLS: با `ENABLE ROW LEVEL SECURITY` و `CREATE POLICY` تعریف می‌شود. برای درج/به‌روزرسانی به `WITH CHECK` هم نیاز است.
- هویت برنامه را می‌توان با `SET app.customer_id = ...` و `current_setting('app.customer_id', true)` به سیاست RLS رساند (مراقب مقدار خالی/ناموجود باشید).
- احراز هویت پیش‌فرض `scram-sha-256` است. رمزها را در Git نگذارید.
- SQL Injection با الحاق رشته در برنامه رخ می‌دهد؛ راه مقابله **کوئری‌های پارامتری** است.
- پشتیبان بی‌آزمون بازیابی، پشتیبان نیست.

### 🧰 وسایل مورد نیاز
دیتابیس `shopdb`، `pg_dump`/`pg_restore`، Python با `psycopg` (برای نمایش SQL Injection).

### 📝 مراحل انجام کار
1. نقش `app_readonly` بسازید که فقط `SELECT` روی `products` و `categories` دارد (بدون دسترسی به `customers`).
2. نقش `app_writer` بسازید که روی `orders` و `order_items` `INSERT` دارد و (برای sequence ها) `USAGE` لازم را. با `SET ROLE` دسترسی‌های مجاز و غیرمجاز را تست کنید و پیام‌های خطا را ثبت کنید.
3. RLS را روی `orders` فعال کنید:

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY user_orders ON orders FOR SELECT TO app_user
  USING (customer_id = nullif(current_setting('app.customer_id', true), '')::bigint);
```

   به نقش `app_user` مجوز `SELECT` بدهید و با `SET ROLE app_user; SET app.customer_id = '5';` ثابت کنید فقط سفارش‌های مشتری ۵ دیده می‌شود. بدون تنظیم `app.customer_id` چند سطر دیده می‌شود؟ چرا؟
4. با مالک جدول وارد شوید و نشان دهید RLS روی او اعمال نمی‌شود. سپس `FORCE ROW LEVEL SECURITY` را بزنید و تکرار کنید.
5. سیاست `INSERT` با `WITH CHECK` بنویسید که کاربر فقط برای خودش سفارش ثبت کند.
6. View `order_summary` (آزمایش ۷) را یک‌بار با و یک‌بار بدون `security_invoker` برای `app_user` تست کنید و تفاوت را توضیح دهید.
7. **SQL Injection:** یک اسکریپت Python با کوئری الحاق‌شده (ناامن) و سپس نسخه پارامتری بنویسید و با ورودی `' OR '1'='1` نتیجه را مقایسه کنید.
8. **پشتیبان‌گیری:** `pg_dump -Fc shopdb -f results/shopdb.dump` بگیرید. دیتابیس `shopdb_restore` بسازید و با `pg_restore` بازیابی کنید.
9. **تأیید بازیابی:** تعداد ردیف همه جداول و یک checksum از داده (مثلاً `md5` تجمیع‌شده) را در دو دیتابیس مقایسه کنید.
10. (اختیاری) بخش PITR را توضیح دهید: `archive_mode`، آرشیو WAL و `pg_basebackup`.

### 📦 تحویلی‌ها
اسکریپت نقش‌ها و مجوزها، جدول آزمون مجوز (مجاز/غیرمجاز)، تست RLS، مقایسه SQL Injection، گزارش تأیید بازیابی.

### ⚠️ خطاهای رایج
- فراموش کردن مجوز روی sequence ها (درج خطا می‌دهد).
- تست RLS با کاربری که مالک جدول یا superuser است.
- گرفتن پشتیبان و هرگز آزمودن بازیابی آن.

### 💡 مثال کاربردی
در SaaS چندمستأجره، RLS تضمین می‌کند هر مشتری فقط داده خودش را ببیند حتی اگر برنامه باگ داشته باشد. پشتیبان تأییدشده در حمله باج‌افزار یا خطای انسانی تنها راه نجات است.

### 🧪 تمرین افزوده
نقش `auditor` را طوری بسازید که فقط به `price_history` دسترسی `SELECT` داشته باشد و هیچ جدول دیگری را نبیند. با یک تریگر عمومی جدول `audit_log` را برای تغییرات `orders` پر کنید.

## 🔬 آزمایش ۱۱: پروژه پایانی: طراحی و پیاده‌سازی یک سیستم پایگاه داده کامل

### 🎯 هدف
طراحی، پیاده‌سازی، بهینه‌سازی، ایمن‌سازی و مستندسازی یک سیستم پایگاه داده کاربردی با PostgreSQL.

### 📋 موضوعات پیشنهادی (یکی را انتخاب کنید یا موضوع خود را تأیید کنید)
1. **رزرو هتل:** اتاق‌ها، مشتریان، رزروها، پرداخت‌ها (جلوگیری از هم‌پوشانی رزرو).
2. **کتابخانه:** کتاب‌ها، اعضا، امانت‌ها و جریمه‌ها.
3. **مدیریت پروژه:** پروژه‌ها، وظایف، اعضا و زمان‌بندی (وابستگی وظایف، درخت زیروظیفه).
4. **فروشگاه آنلاین:** گسترش `shopdb` با نظرات، تخفیف‌ها و موجودی چندانباره.
5. **ثبت‌نام دانشگاه:** دانشجویان، دروس، اساتید، نمرات، پیش‌نیازها و ظرفیت.

### 📝 مراحل انجام کار
1. **مشخصات:** سند کوتاه شامل الزامات، موجودیت‌ها و قواعد کسب‌وکار.
2. **طراحی:** نمودار ER، تحلیل وابستگی‌های تابعی و Schema در حداقل 3NF با قیدهای کامل (PK، FK، `CHECK`، `UNIQUE`).
3. **داده:** اسکریپت تولید داده بازتولیدپذیر (`setseed`) با **حداقل ۱۰۰ هزار ردیف** در جدول‌های اصلی و داده‌های مرزی (NULL، تکراری، خالی).
4. **کوئری‌های تحلیلی:** حداقل ۱۰ کوئری شامل JOIN، `GROUP BY`، زیرکوئری، Window Function و CTE (بازگشتی در صورت مناسب‌بودن).
5. **بهینه‌سازی:** حداقل ۳ کوئری کند را با `EXPLAIN (ANALYZE, BUFFERS)` شناسایی، ایندکس مناسب بسازید و **بهبود را اندازه بگیرید** (قبل/بعد، ۳ تکرار)، همراه با هزینه نوشتن.
6. **منطق تجاری:** رویه/تابع برای فرایند اصلی (مثلاً ثبت رزرو) همراه با تریگر یا قید لازم و **تست‌های خودکار**.
7. **همزمانی:** یک سناریوی رقابتی واقعی (مثلاً دو کاربر برای آخرین اتاق) را با دو اتصال شبیه‌سازی کنید و راه‌حل را ثابت کنید.
8. **امنیت:** نقش‌ها با حداقل دسترسی، یک سیاست RLS (در صورت مناسب‌بودن) و پرهیز از SQL Injection در هر کد برنامه.
9. **پشتیبان‌گیری:** اسکریپت پشتیبان و **اثبات بازیابی** (مقایسه checksum).
10. **بازتولیدپذیری:** با `make reset` یا یک اسکریپت، کل سیستم (Schema، داده، رویه‌ها) از صفر ساخته شود. در صورت امکان `docker compose` فراهم کنید.
11. **گزارش** شامل مشخصات، ER، Schema، تصمیم‌های طراحی، نتایج عملکرد، ملاحظات امنیتی، محدودیت‌ها.
12. **دمو** در جلسه پایانی با پرسش و پاسخ فردی.

## 📌 نکات ایمنی

- فرمان‌های مخرب (`DROP DATABASE`، `DROP TABLE`، `TRUNCATE`، `DELETE` و `UPDATE` بدون `WHERE`) را با دقت اجرا کنید. پیش از اجرا، فرمان را با `SELECT` معادل بررسی کنید.
- پیش از تغییرات بزرگ از دیتابیس پشتیبان بگیرید (`pg_dump`). فقط روی دیتابیس آزمایشگاه کار کنید، نه دیتابیس واقعی.
- از تراکنش برای اجرای آزمایشی استفاده کنید (`BEGIN ... ROLLBACK`).
- برای سناریوهای همزمانی از دو ترمینال جدا استفاده کنید و تراکنش باز را فراموش نکنید.
- در Docker مطمئن شوید داده روی Volume است. پورت را فقط به `127.0.0.1` متصل کنید و از رمز ضعیف خارج از آزمایشگاه استفاده نکنید.
- رمز و کلیدها را در Git نگذارید (از `.gitignore` یا متغیر محیطی استفاده کنید).
- اجرای آزمایش‌های حجیم (تولید داده، ساخت ایندکس) فضای دیسک و زمان لازم دارد؛ پیش از شروع فضای خالی را بررسی کنید.
